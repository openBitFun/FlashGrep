# Sparse 基础索引 + Trigram 增量实验（2026-09-10）

隔离实验版本，生产源码及默认二进制保持不变。实验版本仅允许新建的增量索引，不包含旧 sparse 增量迁移。

## 结论与采用建议

混合版将本轮 50k 更新可见时间中位数从 41.83 s 降到 21.10 s，约减少 50%，与 tgrep 的 21.17 s 基本持平。50k 阶段峰值 RSS 中位数从 1944 MiB 降到 1596 MiB，约减少 18%；tgrep 为 2666 MiB。

大部分测得的查询持平或差异较小，50k 宽匹配为现有版 85.37 ms、混合版 78.47 ms、tgrep 202.32 ms。但存在不能忽略的退化：`(?m)^\s*namespace base \{$` 在 10k 增量时从 5.12 ms 增至 14.17 ms，50k 时从 3.86 ms 增至 54.46 ms（约 14.1 倍；tgrep 16.98 ms）。其他表达式的完整结果如下表，不能用宽匹配表现概括全部正则查询。

此外，批量恢复原内容后的收敛明显变慢：现有版三轮为 2.21 / 2.97 / 4.34 s，混合版为 43.86 / 37.38 / 200.48 s，tgrep 为 16.73 / 26.99 / 14.28 s。这里从全部恢复写入结束开始计时，不能与“第一笔写入至更新可见”的列直接相减。该方向未测纯 tokenizer 开销，长尾根因尚未定位，不能断言是 trigram 本身必然导致。但它是当前原型端到端表现中的实际回退。

因此保留实验原型，不切换生产默认值。这个方向验证了更便宜的增量构建可以追平 tgrep 的大规模更新，但没有实现查询性能的全面提升。下一步可研究让 trigram 仅承担短期增量，后台整理为 sparse；这只是后续设计候选，尚未实现或验证，重新分词成本、发布边界和查询一致性均需单独测量。

本轮只使用普通目录，证明实验路径无需 Git；Git 分支切换正确性由已有测试覆盖，未在本轮做新的 Git 大规模性能矩阵。

## 方法

50,000 个 Chromium 真实源文件的独立副本；普通目录，无 Git。现有 sparse/sparse、sparse/trigram、tgrep 按轮次轮换运行，线程配置与上一轮保持一致。每轮逐步修改至 1,000、10,000、50,000 个文件。新建各版本独立索引后复用；恢复文件时服务继续运行并等待收敛，tgrep 启动后额外等待 20 秒，减少上一轮启动校准与首批更新重叠的问题。

检索使用 files-with-matches RPC，包括 5 类标记/混合查询和 14 个真实 Chromium 查询表达式。所有表达式搜索整个 50k 文件集，此轮不沿用上一轮 C++ 扩展名及子目录过滤，因此不可把绝对查询耗时直接对照上一轮全 Chromium 报告。真实查询期望文件集由 ripgrep 计算，标记查询由已知变更集计算，每次校验完整集合。桌面负载、缓存及后台合并没有隔离；不清空系统缓存。

现有版首轮 50k 出现 180.59 s 长尾，写入为 8.72 s；后两轮为 39.95 / 41.83 s。该样本保留，未剔除，也未用于声称稳定的 8 倍加速。尚未定位长尾根因。tgrep 的 10k 更新时间在 5.76–26.63 s 之间波动；日志确认实验过程中有自动保存活动，但没有证明某次保存就是某个慢样本的原因。三个版本的测量均包含各自正常后台维护的影响，不能当作单独的 tokenizer CPU 性能。

本轮真实查询耗时从发出 RPC 到解析响应结束，文件路径规范化及完整集合断言在计时之外；这些校验仍占用驱动 CPU，后台任务在此期间继续运行。查询前有预热，阶段中没有暂停维护线程，也没有锁定 CPU 或清空页面缓存。文件数量、表达式与线程配置相同，但各引擎的实际缓存状态和自动保存时机并非严格相同。
