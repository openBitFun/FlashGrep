# 生产版本 Chromium 动态检索对比

使用隔离的 Chromium 工作区和相同 1000 个受控文件；原始 chromium-src 未修改。两种工具串行运行，每个场景 3 次，顺序固定随机化。计时为持久 TCP RPC 客户端耗时，包含传输和 JSON 解析。

更新可见时间从本批文件全部写完开始计时，是约 100 ms 轮询下的首次完整结果观测值；连续 3 轮正确后确认。写文件时间单列。下表为中位数，单位均为 ms；查询列使用收敛后的样本。

工作区有一个受 Git 换行符转换影响的 CRLF 文件，flashgrep 合法基线增量为 1；它不在受控 .cc 文件集合中。实验将此基线纳入脏路径计数。两次脚本设置失败和修复调度前的失败尝试均单独保留，未混入当前版本表格。

首次完整结果并不等于索引已更新：删除文件可在候选文件读取阶段被排除。索引状态就绪一列，flashgrep 检查健康、无待处理及预期脏路径计数；tgrep 新增/删除检查文件总数，修改没有等价状态指标，记为 —。两者状态标准不同，不应直接视为同一个内部索引指标。`原生符号`为 ScopedAllowBlockingForTesting。旧/新标记查询的命中文件数量随场景变化，不能把不同查询列当作同一工作量。完整原始数据见各工具 results.json 与 trace.jsonl。flashgrep 表格来自旧产物清理后的完整复测；此前恢复运行中首次 1000 文件删除因回收旧版循环合并产物而超时，原始证据保存在 recovery-run，未混入正常耗时。

早期版本冷启动记录（调度修复前）：flashgrep 第一次建立索引并核对工作区共 207.35 s，其中一次完整发现耗时 124.68 s。该成本与热查询延迟分别报告；此实验尚不能替代较大增量下的重启和内存测量。

最终工作区版复测：flashgrep 使用符号链接规则统一、base/发现串行化和分回合合并后的二进制；tgrep 沿用未修改二进制的完整基线，未与最终版交错复测。SHA-256 为 `76e4f2e1b26c0342af155d46d4dd05f8f80d1fb7f1116d51907ba32e0f64cf6f`。
