# Chromium 上的执行模型重构与复测（2026-09-10）

本轮修改位于 `/Users/user/workspace/flashgrep`。实际源码树为 `/Users/user/workspace/chromium-src`；大批写入使用独立的 50,000 文件副本。实际 Chromium 的 HEAD、已有 `.gitignore` 修改及其哈希在测试前后均保持一致。

## 结论

静态 Chromium 查询的主要瓶颈确实包含执行模型问题：文件名模式不必要地完整计数，Git 基线查询又逐文件打开工作树。改为独立 presence 验证和索引内不可变内容后，文件名查询几何平均加速 2.42 倍（11/14 项更快），完整计数 1.50 倍（8/14 项更快）。这不是所有指标都变好：进程 RSS 增加、索引增大，大批变更后的部分查询仍慢于旧版。下表保留这些退化。

5万文件变更：普通目录可见耗时中位数 49.98 → 44.84 秒，Git 为 41.32 → 39.17 秒；全观察窗口峰值 RSS 分别 2442 → 1466 MiB、2498 → 1535 MiB。全匹配增量查询却从 75.16 → 90.20 ms、74.22 → 84.08 ms；重启首查从约 120 → 303 ms、141 → 331 ms。压缩与按需解码减少了常驻内容，同时增加首次解码成本，不能把内存收益写成全方位提速。

## 设计调整

1. Git 与普通目录统一使用索引内的不可变内容；Git 基线直接读取枚举出的对象 ID，避免查询逐文件打开工作树，也避免 CRLF/过滤器使基线混用工作树内容。旧基线指纹不兼容，需要重建。
2. 将文件存在匹配与完整计数分开：文件名查询在首个匹配后停止，计数继续扫描。删除重复的多 literal 扫描路径。
3. 文件变化发现使用独立观测记录，校验 device/inode/size/mtime/ctime；watcher 指定路径仍强制读内容。观测不绑定 Git HEAD，缓存损坏后重新观测。发现工作使用独立、最多四线程的池。
4. 内容满足收益门槛时用 Zstd 压缩，编码只做一次。基线按需解码；增量解码缓存共享 512 MiB 准入预算，随段 reader 退出回收。缓存不是 LRU，预算也不是 RSS 上限。
5. 保留先前工作区重构的异步发布、版本栅栏、持久化恢复和有界合并。已发布查询可以读到较旧版本；需要覆盖已观察变更时使用相应 freshness 语义，不能将 watcher 当作立即一致性保证。

## 实际 Chromium：全部查询速度

C/C++ 范围为 *.cc / *.h（部分查询只含 *.cc），文件上限 8 MiB；排除 chrome/chrome_elf/dll_hash/** 以对齐 tracked 与 ignore 的收录差异。目录限定采用根相对 glob；chromium_13 限定 chrome/browser。完整规则见 [queries.json](/Users/user/workspace/chromium-real-benchmark-20260910/queries.json)。索引本身按各工具规则建全树，总文件集合并不完全相同；使用十个查询 worker，不清空系统页缓存。

单位 ms，越低越好。旧版与新版分别运行六轮，首轮预热，文件名查询取后五轮中位数；计数取预热后三轮中位数。每个版本检查 140 组完整路径集合或逐文件行计数，均与相同 rg oracle 一致。表中 rg 为前次测量；tgrep 为本轮重测，未与每个新版请求交错。

open、首个查询和后台 ready 是不同边界。已有索引可先查询，ready 不代表 tgrep 已修复所有漏报事件。本轮新版首次查询已单独校验正确。没有清空操作系统页缓存。
同一存储布局的首次建库观测：ensure 271.71 秒，随后 ready 2.53 秒；索引约 3.262 GiB，含约 77 MiB 观测缓存；旧版此前记录约 2.34 GiB，新增不可变源内容会增加磁盘占用。这是中间版本 f145 的冷建库，最终增量缓存版本复用该索引；不能声称测得最终版本的冷建库速度。桌面可用内存估算触发了保守构建，不能与此前约 201.88 秒直接解释为代码的因果退化。
RSS 包括 mmap 页，不等于私有堆或全系统内存；旧版通过文件读取使用的系统页缓存也不等同于进程 RSS。tgrep 在本轮的宽查询明显慢于历史测量，存在桌面内存压力和时序影响，不能把倍率泛化为固定性能差距。
